## 0. 文档目标

本文档用于给出 FactorMiner 当前因子库管理实现的统一重构方案，目标不是再做一版目录调整，而是把以下四件事收口到同一套协议中：

1. 因子定义如何表达
2. 因子如何被发现、筛选和统计
3. 因子如何被执行和评估
4. 因子的保存、删除、迁移和兼容如何治理

最终目标是建立一套可扩展、可兼容、可维护的统一因子库体系，使 WebUI、脚本、挖掘结果保存、评估与后续新数据源扩展都基于同一个事实源工作。

### 0.1 设计理念总览

本蓝图的核心设计理念如下：

1. **单一事实源**：因子定义、执行工件、索引摘要必须由统一协议表达，禁止业务层各自拼装因子视图。
2. **目录只表达数据来源**：`factorlib/` 一级目录只表示 `source_group`，不再混入前端展示语义。
3. **元数据与展示解耦**：底层定义只存结构化事实，前端展示字段由 Catalog 动态生成。
4. **读写路径分离**：查询统一走 `Catalog`，写入统一走 `Lifecycle`，执行统一走 `Executor`。
5. **兼容优先、渐进迁移**：先兼容旧定义读取，再逐步收拢新写入和新查询，不做一次性推倒重写。
6. **透明可追踪**：所有因子必须可以追溯来源、执行工件、来源会话与评估摘要。
7. **索引加速但不替代真相**：`factor_index.json` 只做性能缓存，不替代磁盘原始定义。
8. **扩展不侵入业务层**：新增 `source_group`、新增因子族、扩展算法代理时，不应要求前端和路由层同步改动。
9. **兼容门面逐步变薄**：`factor_storage.py`、`factor_engine.py` 在过渡期保留，但职责逐步下沉到新模块。
10. **治理与运行同等重要**：统一因子库不仅要能保存和执行，还必须能删除、校验、重建索引和清理孤儿文件。

### 0.2 非目标

为避免范围失控，本次蓝图明确以下事项不作为第一轮重构目标：

- 不在第一轮内重写全部已有因子定义文件
- 不在第一轮内全面替换现有 WebUI 页面
- 不在第一轮内移除全部旧接口和旧字段
- 不在第一轮内统一所有评估指标计算实现
- 不在第一轮内调整 `factorlib/` 全部物理目录历史归档结构

## 1. 当前现状判断

### 1.1 已经成型的部分

项目当前已经具备统一因子库的核心雏形：

- `factorlib/` 已采用按数据来源划分一级目录的结构
- `factor_miner/core/factor_storage.py` 已具备动态扫描一级目录的能力
- `factor_miner/core/factor_engine.py` 已具备按 `function / formula / ml_model(算法代理)` 执行因子的能力
- 因子定义已经基本采用透明 JSON 存储，不再依赖纯黑盒模型文件

这说明系统方向是对的，问题主要不是“没有架构”，而是“架构已经演进，但收口没有完成”。

### 1.2 当前主要症状

当前系统处于典型的“过渡期混合状态”：

- 文档存在多套相互冲突的口径
- API 层、Builder、Storage、WebUI 对因子库的认知不一致
- 挖掘结果保存仍在走旧语义接口
- 因子列表页没有复用核心层，而是在路由内自行扫描目录并聚合评估
- 元数据字段既表示物理目录，又承担业务分类和前端展示语义

其结果是：

- 新增能力时很难判断应该改哪一层
- 同一个因子在不同入口下的分类和展示可能不一致
- 后续引入 `onchain`、跨市场、多数据源因子时风险会放大

## 2. 当前问题拆解

### 2.1 架构口径分裂

当前至少存在三套架构叙述：

- `docs/factorlib_structure_guide.md`：按数据源一级分组的 `v4`
- `docs/factor_storage_guide.md`：旧的扁平 `definitions/`、`ml_model/.pkl` 思路
- `docs/new_architecture_guide.md`：进一步简化为 `definitions/ + models/` 的另一套方案

问题：

- 开发者无法基于单一文档理解现状
- 新功能容易按照旧设计继续扩散
- 兼容逻辑与真实主线没有明确边界

### 2.2 接口协议失配

`FactorBuilder`、`FactorAPI`、`FactorMiningAPI` 之间存在真实的参数和返回值错位：

- `FactorBuilder.__init__()` 接收的是 `storage`，上层却传入 `config`
- `build_all_factors()` 要求 `selected_algorithms`，调用方却传 `factor_types`
- `build_all_factors()` 返回字典结果，上层却按 `DataFrame` 使用

问题：

- 某些链路虽然代码存在，但运行行为并不可靠
- 这类问题会让后续重构误判真实依赖关系

### 2.3 发现逻辑分散

目前“发现因子”至少发生在这些位置：

- `TransparentFactorStorage.list_factors()`
- `FactorEngine.search_factors()`
- `webui/routes/factors.py::list_factors()`
- 若干脚本直接扫描 `factorlib/`

问题：

- 每层都在做自己的目录扫描
- 评估聚合和展示映射各自实现
- 查询结果和统计口径难以保持一致

### 2.4 元数据语义混淆

当前主要字段包括：

- `category`
- `subcategory`
- `source`
- `data_requirement`
- `type`

问题：

- `category` 在存储层表示“一级目录”
- 到了前端又被映射成展示分类
- `event_factor`、`mined_factor` 这类值本质上不是数据源，却被塞进 `data_requirement`

结果：

- 数据依赖、因子族别、展示标签混在一起
- 新增筛选维度时会不断叠加临时映射

### 2.5 保存协议不统一

当前因子保存至少有三条路径：

- 脚本通过 `save_function_factor()`
- 挖掘结果通过 `save_minactor_factor()`
- 部分算法代理逻辑试图保存 `algorithm_name / model_file / performance_metrics`

问题：

- 保存入口名不同，语义也不同
- 同一类因子可能因入口不同而写出不同结构
- 旧兼容方法逐步演变成事实上的正式接口

### 2.6 生命周期治理不足

当前删除因子主要删除：

- JSON 定义
- `.py` 函数文件

但没有统一处理：

- 评估历史
- 导出产物
- 索引缓存
- 孤儿文件
- 重名迁移

问题：

- 文件系统逐步变脏
- 列表统计与真实磁盘内容可能不一致

## 3. 重构总目标

本次统一重构的目标如下：

### 3.1 单一事实源

所有因子信息必须由统一协议表达，任何业务层不得直接拼装“自己的因子视图”。

统一事实源包括三类对象：

1. `FactorDefinition`
2. `FactorArtifact`
3. `FactorIndex`

### 3.2 单一入口

以下操作都必须收口到统一服务层：

- 列表
- 搜索
- 分类统计
- 保存
- 删除
- 评估结果挂载
- 迁移与健康检查

### 3.3 单一语义

必须明确区分：

- 数据来源
- 因子族别
- 前端标签
- 执行方式

避免继续把“展示分类”写进“底层存储字段”。

### 3.4 渐进迁移

不采用一次性推翻重写，而是：

- 保留对旧目录和旧字段的读取兼容
- 新写入全部使用新协议
- 逐阶段将路由、API、脚本迁移到新服务

## 4. 统一后的目标架构

### 4.1 分层设计

建议将统一因子库拆成五层：

1. `Schema`：定义统一元数据结构
2. `Repository`：负责文件读写
3. `Catalog`：负责发现、索引、筛选、统计
4. `Executor`：负责执行因子
5. `Lifecycle`：负责保存、删除、迁移、健康检查

### 4.2 分层职责

| 层 | 模块建议 | 核心职责 | 不负责 |
|---|---|---|---|
| Schema | `factor_schema.py` | 定义标准数据结构 | 文件扫描 |
| Repository | `factor_repository.py` | 定义/评估/函数/公式文件读写 | UI 映射 |
| Catalog | `factor_catalog.py` | 列表、搜索、索引、统计、缓存 | 实际执行 |
| Executor | `factor_executor.py` | `function / formula / algorithm_proxy` 运行 | 存储策略 |
| Lifecycle | `factor_lifecycle.py` | 保存、删除、迁移、清理、校验 | 前端展示 |

### 4.3 目标调用关系

```text
WebUI / API / Scripts
        |
        v
FactorCatalogService / FactorLifecycleService / FactorExecutor
        |
        v
FactorRepository
        |
        v
factorlib/ + factor_index.json
```

原则：

- 上层不得直接遍历 `factorlib/`
- 上层不得自己拼装“因子摘要”
- 所有查询都先走 `Catalog`
- 所有修改都先走 `Lifecycle`

## 5. 统一元数据模型

### 5.1 核心字段设计

建议将当前定义统一为以下字段：

```json
{
  "factor_id": "wq101_alpha001",
  "name": "WorldQuant Alpha 001",
  "description": "Alpha 001 factor",
  "source_group": "basic_kline",
  "factor_kind": "wq101",
  "computation_type": "function",
  "artifacts": {
    "function_file": "basic_kline/functions/wq101_alpha001.py",
    "entry_point": "calculate"
  },
  "parameters": {},
  "dependencies": [],
  "traits": {
    "is_event": false,
    "is_mined": false,
    "is_cross_sectional": false
  },
  "tags": ["technical", "alpha_family", "wq101"],
  "output_type": "series",
  "metadata": {
    "version": "1.0.0",
    "created_at": "2026-05-06T10:00:00",
    "updated_at": "2026-05-06T10:00:00",
    "checksum": "abcd1234"
  }
}
```

### 5.2 字段语义约束

#### `source_group`

只表示该因子依赖的数据来源，必须与物理一级目录一致，例如：

- `basic_kline`
- `derivatives`
- `funding`
- `onchain`

禁止表示：

- `event_factor`
- `mined_factor`
- `technical`

#### `factor_kind`

表示因子族别或业务类型，例如：

- `technical`
- `event`
- `mined`
- `qlib158`
- `qlib360`
- `wq101`
- `derivatives_flow`
- `funding_level`

#### `traits`

表示可枚举的布尔或轻量语义，不参与物理存储映射，例如：

- `is_event`
- `is_mined`
- `is_cross_sectional`
- `requires_extra_data`
- `realtime_supported`

#### `tags`

用于搜索和 UI 辅助筛选，不承载核心逻辑。

#### `artifacts`

只保存执行依赖的工件引用，不保存大块重复源码。

### 5.3 旧字段到新字段映射

为保证渐进迁移，旧定义在读取阶段需要被规范化到新 schema。建议映射规则如下：

| 旧字段 | 旧语义 | 新字段 | 迁移规则 |
|---|---|---|---|
| `category` | 既可能表示一级目录，也可能表示技术分类 | `source_group` 或 `factor_kind` | 若值命中一级目录集合，则映射到 `source_group`；否则映射到 `factor_kind` |
| `subcategory` | 二级用途标签 | `factor_kind` 或 `tags` | 若 `factor_kind` 为空则优先映射到 `factor_kind`，否则放入 `tags` |
| `type` | 前端展示分类 | 不直接保留 | 由 `Catalog` 动态生成，不写回底层定义 |
| `data_requirement` | 前端过滤条件 | `source_group` 或 `traits` | 若值为真实数据源则映射到 `source_group`，若为 `event_factor/mined_factor` 则转为 `traits` |
| `computation_data.function_file` | 函数工件路径 | `artifacts.function_file` | 原样迁移 |
| `computation_data.formula` | 内嵌公式 | `artifacts.formula_inline` 或 `formulas/<id>.txt` | 第一阶段允许兼容内嵌，后续迁移到文件 |
| `computation_data.algorithm_name` | 算法代理名称 | `artifacts.algorithm_name` | 原样迁移 |
| `metadata.is_window` | 窗口型因子标记 | `traits.is_window` | 迁移到 `traits` |
| `metadata.min_warmup_bars` | 最小预热长度 | `traits.min_warmup_bars` | 保留为轻量执行属性 |

### 5.4 规范化读取策略

建议 Repository 层提供统一的“规范化读取”逻辑：

1. 读取磁盘原始 JSON
2. 判定版本号或字段特征
3. 调用对应版本的适配器
4. 输出统一 `FactorDefinition`

示意：

```python
def normalize_legacy_definition(raw: dict) -> FactorDefinition:
    if "source_group" in raw and "factor_kind" in raw:
        return FactorDefinition.from_dict(raw)
    return LegacyDefinitionAdapter().adapt(raw)
```

原则：

- 上层永远只消费统一 schema
- 兼容转换只发生在 Repository 内部
- 旧格式不在 WebUI、API、Executor 中继续扩散

## 8. 统一查询与索引方案

### 8.1 为什么需要索引

当前列表页每次都：

- 扫描目录
- 逐个打开 JSON
- 逐个聚合评估记录

当因子数量继续增长时，问题会变成：

- 页面响应变慢
- API 返回不稳定
- 统计逻辑分散在业务层

因此建议引入 `factor_index.json` 作为运行期缓存索引。

### 8.2 索引内容

索引不替代真实定义，只缓存摘要信息，例如：

- `factor_id`
- `name`
- `source_group`
- `factor_kind`
- `computation_type`
- `tags`
- `traits`
- `created_at`
- `latest_evaluation_summary`
- `artifact_paths`

### 8.3 索引更新策略

索引更新时机：

1. `save_factor()` 成功后更新
2. `delete_factor()` 成功后更新
3. `save_evaluation()` 成功后更新摘要
4. 手工执行 `rebuild_index()` 时全量重建

### 8.4 前端与 API 使用方式

WebUI 和 API 不再自行扫描目录，而是统一调用：

- `catalog.list_factors()`
- `catalog.get_summary()`
- `catalog.get_stats()`

这样前端只消费标准化摘要，不关心底层文件结构。

### 8.5 索引文件建议格式

建议 `factor_index.json` 采用“版本化 + 摘要条目”的结构：

```json
{
  "schema_version": "1.0",
  "generated_at": "2026-05-06T12:00:00",
  "source_groups": ["basic_kline", "derivatives", "funding"],
  "factors": [
    {
      "factor_id": "wq101_alpha001",
      "name": "WorldQuant Alpha 001",
      "source_group": "basic_kline",
      "factor_kind": "wq101",
      "computation_type": "function",
      "traits": {
        "is_event": false,
        "is_mined": false
      },
      "artifact_paths": {
        "definition": "basic_kline/definitions/wq101_alpha001.json",
        "function": "basic_kline/functions/wq101_alpha001.py"
      },
      "latest_evaluation_summary": {
        "evaluated_at": "2026-05-05T08:00:00",
        "ic_pearson": 0.012,
        "ic_spearman": 0.018,
        "icir": 0.11
      }
    }
  ]
}
```

约束：

- 索引只存摘要，不存完整源码
- 索引损坏时必须可由磁盘全量重建
- 索引缺失不能影响因子可用性，只影响性能

### 8.6 缓存一致性策略

建议采用“写时更新 + 兜底重建”的策略：

- 正常路径：`save_factor/delete_factor/save_evaluation` 时同步更新索引
- 异常路径：发现索引缺项或摘要不一致时触发后台重建
- 启动路径：应用启动时仅检查索引版本，不做无条件全量重扫

这样可以兼顾性能和恢复能力。

## 9. 统一执行协议

### 9.1 执行类型收敛

建议将执行类型明确收敛为三类：

1. `function`
2. `formula`
3. `algorithm_proxy`

其中：

- 旧的 `ml_model` 在兼容层解析为 `algorithm_proxy`
- 真正的预训练模型文件路径不再作为主流因子形态直接暴露给上层

### 9.2 `function`

适用于：

- 技术指标
- 统计指标
- 共享算子类因子

要求：

- `artifacts.function_file` 必填
- `entry_point` 默认 `calculate`

### 9.3 `formula`

适用于：

- 简单表达式类因子
- 适合展示和批量注册的规则型因子

要求：

- 建议以文件形式保存到 `formulas/`
- 不再把长公式直接塞进 JSON

### 9.4 `algorithm_proxy`

适用于：

- GP/RL 挖掘结果
- 用户算法代理因子
- 需要通过算法模块解释的共享生成式因子

要求：

- 明确 `algorithm_name`
- 明确 `factor_name` 或 `proxy_key`
- 明确来源会话和表达式元数据

## 10. 统一保存协议

### 10.1 新的唯一保存入口

建议新增唯一正式保存入口：

```python
save_factor(
    factor_def: FactorDefinition,
    artifacts: dict | None = None,
    overwrite: bool = False,
    validate: bool = True,
)
```

### 10.2 保存行为

保存过程建议分为以下步骤：

1. 校验 `factor_id` 唯一性和命名规范
2. 校验 `source_group` 合法性
3. 校验 `computation_type` 与 `artifacts` 匹配
4. 写入函数或公式工件
5. 写入标准定义 JSON
6. 更新索引缓存
7. 返回结构化结果

### 10.3 兼容旧接口

以下旧接口仅作为兼容包装层存在：

- `save_function_factor()`
- `save_technical_factor()`
- `save_minactor_factor()`

兼容层职责：

- 解析旧参数
- 组装新 `FactorDefinition`
- 调用统一 `save_factor()`

兼容层不允许再承载新的业务语义。

### 10.4 挖掘结果保存规范

挖掘结果保存不再伪装成“技术因子函数保存”，而应明确写成：

- `source_group = basic_kline` 或对应真实数据源
- `factor_kind = mined`
- `computation_type = algorithm_proxy`
- `traits.is_mined = true`
- `metadata.source_session_id = xxx`
- `metadata.expression = xxx`

### 10.5 三类保存示例

#### 示例 A：普通函数因子

```json
{
  "factor_id": "ema_20",
  "source_group": "basic_kline",
  "factor_kind": "technical",
  "computation_type": "function",
  "artifacts": {
    "function_file": "basic_kline/functions/ema_20.py",
    "entry_point": "calculate"
  }
}
```

#### 示例 B：规则公式因子

```json
{
  "factor_id": "close_to_ma20_ratio",
  "source_group": "basic_kline",
  "factor_kind": "technical",
  "computation_type": "formula",
  "artifacts": {
    "formula_file": "basic_kline/formulas/close_to_ma20_ratio.txt"
  }
}
```

#### 示例 C：挖掘代理因子

```json
{
  "factor_id": "mined_cross_sectional_20260506_001",
  "source_group": "basic_kline",
  "factor_kind": "mined",
  "computation_type": "algorithm_proxy",
  "artifacts": {
    "algorithm_name": "gp_cross_sectional",
    "proxy_key": "mined_cross_sectional_20260506_001"
  },
  "traits": {
    "is_mined": true,
    "is_cross_sectional": true
  },
  "metadata": {
    "source_session_id": "session_xxx",
    "expression": "rank(close / ts_mean(close, 20))"
  }
}
```

## 14. 风险与应对

### 14.1 风险：旧数据兼容失败

应对：

- 先实现只读兼容
- 批量迁移前先做 dry-run
- 保留归档目录，不直接覆盖

### 14.2 风险：WebUI 行为变化

应对：

- 新旧列表接口并行一段时间
- 在 Catalog 层保持旧字段别名输出

### 14.3 风险：执行器重构影响已有因子

应对：

- 先覆盖 `function` 路径
- 再迁移 `formula`
- 最后迁移 `algorithm_proxy`

### 14.4 风险：性能问题被延后暴露

应对：

- 第 2 阶段同步引入索引缓存
- 对列表接口加统计和耗时日志

## 15. 验收标准

完成本蓝图后，统一因子库应满足以下标准：

### 15.1 功能标准

- WebUI、API、脚本的因子列表口径一致
- 新因子只通过一个正式入口保存
- 删除因子可联动清理评估和索引
- 新增 `source_group` 时无需改前端业务代码

### 15.2 结构标准

- 所有定义都能被解析为统一 schema
- 所有查询都通过 Catalog 完成
- 所有执行都通过 Executor 完成
- 所有修改都通过 Lifecycle 完成

### 15.3 治理标准

- 存在可执行的健康检查命令
- 存在可执行的索引重建命令
- 存在孤儿文件识别机制
- 旧接口均进入兼容层并带有废弃说明

### 15.4 测试标准

建议补齐以下测试类型：

- **Schema 测试**：验证新定义与旧定义都能规范化解析
- **Repository 测试**：验证定义、工件、评估文件的读写和删除
- **Catalog 测试**：验证列表、搜索、索引重建、统计摘要
- **Executor 测试**：验证 `function / formula / algorithm_proxy` 三种执行路径
- **Lifecycle 测试**：验证保存、删除、迁移、孤儿清理
- **回归测试**：抽取若干已有 `basic_kline`、`derivatives`、`funding` 因子做端到端验证

### 15.5 最小回归样本建议

建议至少选取以下样本做回归：

| 因子类型 | 示例 | 目的 |
|---|---|---|
| 普通函数因子 | `ema` / `rsi` | 验证基础函数执行与保存 |
| qlib/WQ 家族因子 | `wq101_alpha001` | 验证共享算子与函数寻址 |
| 公式因子 | 任一 `formula` 类型因子 | 验证公式工件读取 |
| 衍生品因子 | `oi_change_zscore` | 验证 `source_group=derivatives` |
| 资金费率因子 | `funding_rate_ma` | 验证 `source_group=funding` |
| 挖掘代理因子 | 任一 GP/RL 入库因子 | 验证 `algorithm_proxy` 路径 |

## 16. 兼容与废弃策略

### 16.1 兼容期原则

兼容期内遵循以下原则：

1. 旧定义允许读，不鼓励再写
2. 新入口统一写新 schema
3. 旧接口保留方法名，但内部只做参数翻译
4. 所有废弃接口都输出明确 warning 或日志

### 16.2 废弃顺序

建议废弃顺序如下：

1. 先废弃旧文档口径
2. 再废弃旧保存语义
3. 再废弃路由和脚本中的直接扫盘逻辑
4. 最后废弃旧字段写入

### 16.3 不建议立即删除的兼容点

以下兼容点建议保留至少一个迭代周期：

- `category` 旧字段读取
- `subcategory` 旧字段读取
- `ml_model` 到 `algorithm_proxy` 的别名兼容
- 内嵌 `formula` 的读取兼容
- `save_minactor_factor()` 的兼容包装

原因：

- 现有库中仍有大量历史定义
- 脚本和示例代码可能仍依赖旧字段
- 一次性清退的收益低于风险

## 17. 第一阶段后的推荐目录形态

第一阶段完成后，不要求磁盘目录立即全部迁完，但推荐逻辑上达到以下形态：

```text
factor_miner/core/
├── factor_schema.py
├── factor_repository.py
├── factor_catalog.py
├── factor_executor.py
├── factor_lifecycle.py
├── factor_storage.py          # 兼容门面，逐步变薄
└── factor_engine.py           # 兼容门面，逐步委托给 executor
```

过渡原则：

- `factor_storage.py` 暂时保留，但逐步退化为门面层
- `factor_engine.py` 暂时保留，但执行逻辑迁入 `factor_executor.py`
- 新模块先引入，不与旧模块做一次性互斥替换

## 18. 推荐实施顺序

建议按以下优先级实施：

1. 先修 `FactorBuilder / FactorAPI / FactorMiningAPI` 的接口失配
2. 再抽 `FactorCatalogService`，让列表与统计口径统一
3. 再实现统一 `save_factor()`，收拢保存协议
4. 最后拆分执行与生命周期治理

原因：

- 接口失配会直接影响当前可用性
- Catalog 是最容易收口、收益最大的模块
- 保存协议统一后，新增功能就不会继续扩散旧语义

## 19. 最终结论

本次重构的重点不是继续调整 `factorlib/` 的目录树，而是建立统一协议，让：

- 因子定义有单一 schema
- 因子发现有单一 catalog
- 因子执行有单一 executor
- 因子治理有单一 lifecycle

只要这四个目标达成，当前因子库就能从“过渡期架构”升级为“稳定可扩展架构”，后续接入新的数据源、算法族、跨市场因子与实时能力时都将具备明确边界和稳定演进路径。

从当前进度看，蓝图、任务拆解和核心代码骨架已经具备，下一步的重点不再是继续抽象，而是把第 1 阶段和第 2 阶段真正接入现有主路径，使统一 schema 和统一 catalog 先在现网代码中落地。
